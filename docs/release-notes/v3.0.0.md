## 新增

TODO：本次新增的能力，一条一个要点，写清楚用户能看到什么变化。**以下已补充，其余待续。**

- **脚本可以直接回头调用面板了，不用再申请 Open API 应用**：任务运行时新注入 `DAIDAI_API_BASE`（接口根地址）和 `DAIDAI_TOKEN`（配套令牌），两个拼起来就能发 HTTP 请求——发通知、读写环境变量、查任务和日志、触发订阅拉取都不用把账号密码写进脚本。完整用法、三种语言的可直接复制示例、以及踩坑提醒见新增的[脚本内调用面板能力](../script-api.md)。原有的 `DAIDAI_NOTIFY_URL` / `DAIDAI_NOTIFY_TOKEN` 原样保留，既有脚本不受影响。
- **环境变量新增「按名字写回」接口 `PUT /api/v1/envs/by-name`**：脚本跑完想更新 Cookie 这类需求，此前走 HTTP 必须先查 id 再更新，而 `ddp env set` 又是另一套语义。现在两边对齐：不存在则创建、存在一条则更新、**存在多条则直接报错**并要求用备注消歧。多条报错是刻意设计——同名多条意味着多账号，脚本读到的是合并且转义后的串，整段写回任意一条都会破坏结构，报错比静默改错更安全。`POST /api/v1/envs` 的「纯 insert」行为保持不变。
- **Magisk 模块支持 Android 6.0**：安装门槛从 Android 7.0 (API 24) 降到 6.0 (API 23)。原来那个数字是保守猜的，仓库里找不到任何技术上真正需要它的东西——模块走的是 chroot 模式，不依赖 user namespace，所以老内核不构成阻塞。**但真正的准入不再是版本号，而是安装时实际探测**（见下条），低于 Android 8.0 时会提示「可以尝试但不保证可用」。
  > 坦白说：我们没有 Android 6 真机可以验证。这次改动的价值是「装不上时会明确告诉你为什么」，而不是「保证 Android 6 一定能用」。
- **Magisk 模块安装时会先探测容器能否启动**：在解压完 rootfs、开始装依赖之前实际进容器跑一条命令。探测失败立刻中止并给出三个方向的排查建议（SELinux 策略 / 内核不支持挂载 / root 方案版本过旧），不会再让你等几分钟装完依赖、重启之后才发现面板起不来。这一步对所有 Android 版本都生效。
- **Linux 压缩包随包提供 `ddp` 命令行**：此前 `ddp` 只在 Docker 镜像、Windows 压缩包和 Magisk 模块里有，Linux 二进制部署的用户拿不到。现在四个架构的 `tar.gz` 里都带上了，解压即用。压缩包内文件名就叫 `ddp`，可以直接放进 `PATH`。
  > 已在用二进制版的用户走面板内「检查更新」升级到本版本后，安装目录里会多出一个 `ddp` 文件，属于预期变化。

## 修复

TODO：以下 5 条来自未发布的 `v2.3.9`（相关代码已在仓库中，随 `v3.0.0` 一并发出），**本次大版本自身的修复项待补充**。格式沿用历史版本：**一句话结论** + 现象 + 现在的行为 + 影响范围（哪些场景不受影响）。

- **修复企业微信应用 mpnews 图文消息正文不换行**：mpnews 的正文（content）按 HTML 渲染，此前正文里的换行不生效。现在正文中的换行会正确转换为 `<br>` 显示；描述（digest）等纯文本字段以及 text、markdown 等其它消息类型的换行行为保持不变，不受影响。
- **修复 Edge/Chromium 下点击最小化被强制拉回全屏**：窗口最小化时浏览器会上报窗口宽度为 0，此前被误判为移动端，导致弹窗全屏、侧栏收起、页面切到移动端布局（切到别的标签页再切回来才恢复）。现在对“宽度为 0/页面隐藏”的异常尺寸加了守卫，最小化不再翻转布局；真实移动端与正常窗口缩放不受影响。
- **修复桌面版 Python 版本缺失直接启动失败**：当任务配置的 Python 版本（如 3.12）本机未安装、但装了其它受支持版本（如 3.11）时，面板会自动回退到已安装的版本运行，并在日志中提示“已回退到 x.x”，不再直接报“Python x.x 不可用”而中断。Windows 上仅通过 `py` 启动器安装的 Python 也能被正确识别。任务表单会标注未安装的版本，新任务默认选中已安装的版本。桌面/二进制版与面具（Magisk）版回退行为一致；已安装所请求版本时仍然尊重该版本、不会回退。
- **修复随机延迟误延迟手动执行的任务**：设置“随机延迟最大秒数”后，此前手动点击执行的任务也会被排队延迟。现在随机延迟只跳过手动执行——手动点击立即运行；定时（cron）与开机运行仍按配置错峰，开机任务的错峰能力不再丢失。想让某个任务开机不等待，把它的“随机延迟秒数”显式设为 0 即可。
- **修复「定时任务最大并发数」与「不允许多实例」从未真正生效**：此前调度器只在“派发”阶段计数，任务一启动就释放了槽位，导致并发数填 1 还是 128 都不限制同时运行的任务数，「不允许多实例」也拦不住执行期间的重复触发。现在槽位会一直持有到任务真正结束（含全部重试），并发数成为真实上限，同一任务在执行期间的重复触发会被拒绝。随机延迟改为在占用槽位之前等待，不会再空占并发名额；调度阶段出现异常时名额会被正常归还，不会一次异常就永久少掉一个并发名额。
- **修复开机任务一拥而上**：并发闸门生效后，把「定时任务最大并发数」设为 1，开机运行的任务就会按任务排序（`sort_order`）逐个执行，前置任务排在第一位即可，不必再把前置脚本复制进每个任务。

  > **注意随机延迟与排序的相互作用**：随机延迟是通过“等待到期后重新排队”实现的，所以**带非零随机延迟的开机任务，实际先后由延迟到期时间决定，不再遵循 `sort_order`**（并发数为 1 时仍然保证一次只跑一个，只是顺序是乱的）。两种编排方式二选一即可：
  >
  > - **靠排序**：把开机任务的「随机延迟秒数」全部显式设为 0，顺序完全由 `sort_order` 决定；
  > - **靠延迟**（v2.3.8 及更早的老办法）：前置任务设 0、其余保留延迟，前置任务因为不等待而必然先入队先执行。
- **修复关机时被运行中的任务拖住**：关闭或重启面板时，现在先停止接收新任务并中断执行中的子进程，再回收调度线程，不用等满超时。
- **修复多设备登录后旧会话无限加载**：当同时在线设备超过“同时在线人数”限制、较早的登录被顶下线后，旧设备/页面此前会卡在无限加载，必须退出重新登录。现在旧会话的请求会正确失效并跳转到登录页，不再卡死。
- **修复注入脚本的面板令牌有效期长达一年且无法作废**（安全）：任务运行时会往脚本环境里注入一枚面板令牌供内置通知 helper 使用。此前当任务没有设置「超时时间」时——**这是数据库默认值，也就是绝大多数任务**——签发的是有效期整整一年的令牌；而且签发时丢弃了令牌 ID，面板自己都无法作废它，用户登出、改密码都不影响，唯一手段是更换 JWT 密钥（会把所有登录用户一起踢下线）。现在改为**用完立刻作废、有效期只做兜底**：任务收尾（含正常结束、失败、超时被杀、脚本异常崩溃）即刻吊销，未设超时的兜底有效期从一年收到 7 天。同一处理覆盖 `ddp python` / `ddp shell` 与脚本编辑器的调试运行。作废后再用它调接口返回 `401`。令牌的权限范围与注意事项见[脚本内调用面板能力](../script-api.md#6-安全说明)。
- **修复过期的令牌黑名单记录从不清理**：登出、会话被顶下线、脚本令牌作废都会往黑名单写一行，但此前没有任何地方删除已过期的记录（过期令牌本身就过不了校验，黑名单行留着已无意义）。现在随既有的日志清理周期一并清除。
- **修复 README 文档导航里的失效链接**：两处指向一份并不存在的「系统配置与运维说明」，已移除。
- **修复 Magisk 模块安装失败却报告成功**：此前安装脚本几乎不检查失败——从不确认容器运行时 `rurima` 是否存在就直接调用，进容器装依赖那一整段也没有任何退出码检查，最后**无条件**打印「安装完成！」。于是「依赖一个都没装上」表现为安装器显示成功、重启后面板起不来或所有任务都跑不了，用户完全无从判断哪一步出的问题。现在：`rurima` 缺失立即中止；依赖装完后会实际验证 `python3` / `node` / `npm` / `git` / `bash` 能否执行并报出版本，缺哪个就列出哪个；只有全部通过才会打印「安装完成！」。所有新增的中止点都落在既有的数据备份保护范围内，中止后用户数据完好、重装会自动恢复。
  > 此前 `Magisk/README.md` 的 FAQ 承诺「超时失败模块会自动 abort」——那句话对下载和解压是成立的，对依赖安装并不成立。现在两者都成立了，但走的是不同机制（下载看退出码，依赖看装完后的实际可用性），文档已按实现拆开说明。

## 破坏性变更

TODO：大版本如果有不向后兼容的改动（配置项重命名、接口字段调整、数据结构迁移等），必须在这里逐条列出并给出迁移办法。**没有则整节删除。**

- **「定时任务最大并发数」首次真正生效（默认 5）**：升级前这个开关形同虚设，所有任务实际不受限并发；升级后同时运行的任务最多 5 个，其余排队等待。任务多的用户会直观感到“变慢了”，这是修复不是退化。需要更高并发请到 设置 → 调大「定时任务最大并发数」。
- **Magisk 模块不再接受 x86_64 设备**：模块自带的容器运行时 `rurima` 只有 AArch64 构建（实测 `e_machine=0x00b7`），随包的两个离线 apk 也都是 `arch = aarch64`。此前架构检查同时放行 `x64`，于是 x86_64 设备能通过检查、能选中 amd64 后端，然后在启动容器时失败——而安装器**照样打印「安装完成！」**，用户重启后才发现面板起不来，且没有任何线索。现在安装时会被明确拦截，并说清是「模块缺 x86_64 的容器运行时」而不是「你包下错了」。发布产物也随之只打 arm64，手机端少下几十 MB 永远用不上的二进制。
  > 如果你的 x86_64 设备此前「装成功」过：那个面板本来就没跑起来。这是把静默失败变成明确失败，不是能力回退。
- **卡死的任务会占用并发名额**：升级前一个 hang 住的任务不影响别的任务；升级后它会一直占着一个名额，若把名额占满调度会停摆。请给可能卡死的任务设置「超时时间」（默认 0 表示不限制）。
